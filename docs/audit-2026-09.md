# Audit du code — Celestial Walker (Nuxt 3 / Three.js)

Date : 2026-09-05. Périmètre : l'intégralité du dépôt (≈12 000 lignes hors `node_modules`), lu fichier par fichier : composables, composants, configs, types, données JSON, i18n, CI, Dockerfile, docs.

Limites : `node_modules` n'est pas installé et `eslint.config.mjs` est absent du dépôt (gitignoré), donc ni `pnpm lint` ni `nuxt typecheck` n'ont pu être exécutés. L'audit est statique.

Légende sévérité : **B** = bug ou comportement incorrect · **A** = architecture / dette · **P** = performance · **O** = outillage, build, docs.

---

## 1. Ce qui est bien et doit survivre à la migration

- **Pipeline data-driven** : les features visuelles (nuages, atmosphère, shader jour/nuit, rugosité depuis spéculaire, anneaux) s'activent par présence des textures / propriétés dans le JSON. Ajouter un corps = ajouter une entrée JSON. (`composables/factories/useCelestialBodyFactory.ts`)
- **Mécanique orbitale sérieuse** : équation de Kepler résolue par Newton-Raphson, anomalie vraie, ellipse avec foyer à l'origine, conversion écliptique → plan équatorial solaire. (`useSimulationManager.ts`, `utils/coordinateConversion.ts`, `useOrbitFactory.ts`)
- **Hiérarchie de scène claire** : `Orbital Plane (Ω)` → `Orbit pivot (i)` → `System` → `Mesh` ; les satellites vivent dans le `System` du parent. Elle se transpose telle quelle en JSX.
- **Shader jour/nuit** injecté via `onBeforeCompile` sur un `MeshStandardMaterial`, uniform mis à jour par la simulation.
- **Identité visuelle HUD** (SVG responsive, coins, indicateur de zoom, drawer, fenêtres à bordure animée), i18n complète EN/FR avec descriptions riches, tutoriel spotlight, préloader.
- **Documentation JSDoc** systématique et un `DEV_GUIDE.md` précis sur le graphe de scène et les patterns Three.js.

## 6. Synthèse

Le projet est fonctionnellement riche et la couche "physique / données" est de bonne qualité. Les problèmes se concentrent sur trois axes :

1. **Réactivité Vue appliquée à des objets Three.js** (A1, A2, A3) : c'est la dette structurelle principale, et la raison pour laquelle une réécriture en React Three Fiber est pertinente plutôt qu'un simple refactor.
2. **Assets et rendu** (P1 à P3) : indépendant du framework, à traiter dans la migration mais après la parité fonctionnelle.
3. **Outillage** (O2, O3, O4, O6) : lint non versionné, pas de tests, CI incomplète, Docker root.

Les bugs B1 à B13 sont individuellement petits ; ils sont listés pour être **absents de la version React**, pas pour être corrigés dans la version Vue (sauf décision contraire).
